# Can a Custom UI resolver hand sequencing to an async event and collect the answer later?

Research note, 2026-09-01. Sources are Atlassian's Forge developer documentation and changelog, the npm registry and the Pyodide repository, fetched today. Every claim is labelled **documented** (the page says it) or **not established** (no page fetched says it). No experiment was run for this note and nothing was deployed; the one measured figure quoted, 3.4 s per ask on Forge's CPU, is the handoff's and is not re-measured here.

The question: a sequencing calculation of roughly 3.4 s per ask, up to 50 asks, so up to about 170 s of CPU, started from a Custom UI resolver that has a 25 s budget, run somewhere with a longer budget, and collected by the Custom UI afterwards.

## Summary

1. **Declaration: a `consumer` module, distinct from `function`, pointing at a `function` module.** `modules.consumer[]` has `key`, `queue`, `function` and optional `crossVersion`; the function it names carries `timeoutSeconds` and, through `runtime.memoryMB`, its own memory. Whether that function runs in a separate container from the resolver's is not documented.
2. **Versioning: adding a consumer is not on the documented major-version list.** The list is scopes, CSP options, external URLs, dynamic web triggers, egress categories, `inScopeEUD`, licensing, providers, remotes and customer-managed egress; "Forge creates a new minor version whenever you deploy app changes that don't result in a new major version." Nothing on the page exempts a `development` environment, and the only environment-specific sentences are about `production`. The repository's own record that a `jira:customField` block deployed as major (`CLAUDE.md`, ADR 0025) is not contradicted by the page but is not explained by it either; the honest answer is that the page's list is not presented as exhaustive and the classification is settled by deploying, which CLAUDE.md already says.
3. **Consumer limits: 900 s confirmed, memory 512 MB default and 1,024 MB maximum, both per function.** `timeoutSeconds` is 1 to 900 and "applies to scheduled triggers and asynchronous event consumers only"; the consumer's default is 55 s. No page classifies a change to `memoryMB` or `timeoutSeconds` as major, and neither appears on the major list.
4. **Payload 200 KB per push (100 KB per event once the function's timeout exceeds 55 s), 50 events per push, 500 events per minute per app, retries automatic and unbounded in count within a 24 h retention window, and a resolver may push.** A timeout is an "app-level error", which is retried; a retried event carries `retryContext` with `retryCount`, `retryReason`, `retryData` and `retentionWindow`. Delivery is at least once. The LLM tutorial's resolver does exactly `queue.push([{ body: payload }])` and returns.
5. **Delay: yes, `delayInSeconds` up to 15 minutes. Cancel: yes, `queue.getJob(jobId).cancel()`. Status: `getStats()` returns `{success, inProgress, failed}` counts, nothing else.** No result payload, no per-event state and no documented lifetime for the job record, so a status row in storage is still needed to carry the answer; `getStats()` can only say whether the job has finished.
6. **Storage: 240 KiB per value, 500-character keys, 1,000 requests per second and 4,000 reads plus 4,000 writes (10 KB units) per minute per installation, a TTL of up to one year settable per key, `kvs.get` strictly consistent.** Key-value storage suffices; custom entities add indexes and queries that a poll-by-key does not need.
7. **The 25 s resolver limit is documented; no bridge `invoke` timeout is documented separately; a resolver returning before its pushed work completes is the documented pattern.** Front-end request payloads are capped at 500 KB and responses at 5 MB.
8. **No function bundle size limit is documented.** The only documented bundle limits are for static resources (100 MB per resource) and the manifest file (200 KB).
9. **Runtime Node.js 22 or 24 (`nodejs24.x` recommended). Pyodide's current npm release is 314.0.6, dated August 25, 2026, Python 3.14.2.**
10. **No Forge changelog entry between 2026-08-13 and 2026-09-01 touches async events, consumers, function limits, storage limits or versioning.** Entries for 2026-08-01 to 2026-08-12 could not be reached (closing section).

## 1. Declaring the queue and its consumer

**Documented.** The module is `consumer`, listed under `modules` beside `function`, not inside it. Its properties: `key` (required, `^[a-zA-Z0-9_-]+$`), `queue` (required, "The name of the queue for which the consumer processes the events asynchronously"), `function` (required for `@forge/events` v2 and later, "A reference to the function module that will be invoked when events are pushed to the queue of this consumer module"), `resolver` (deprecated, v1.x only) and `crossVersion` (optional boolean: "When set to `true`, this property ensures that async events are processed even if the application version changes before the event processing begins"). The page's example is a `consumer` with `queue: my-queue` and `function: myQueueFunction`, plus a `function` with that key and `handler: index.handler`. Last updated Apr 3, 2026. [https://developer.atlassian.com/platform/forge/manifest-reference/modules/consumer/]

**Documented.** The queue is not declared anywhere else; the name in the manifest is the name passed to `new Queue({ key: 'queue-name' })` in code. The API reference's manifest example gives the consumer's function `timeoutSeconds: 600`. Last updated Jun 15, 2026. [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/]

**Documented.** The consumer's function is an ordinary `function` module with the same properties as any other: `key` (max 23 characters), `handler` (`file.function`), optional `providers`, optional `timeoutSeconds`, optional `runtime` ("Override Forge runtime configuration defined in app.runtime. For now, only memoryMB property is allowed"). Last updated Jan 13, 2026. [https://developer.atlassian.com/platform/forge/manifest-reference/modules/function/]

**Documented.** The handler shape under `@forge/events` v2 and later: "export an async function from the file specified in the manifest `handler` property: `export async function handler(event: AsyncEvent, context) {...}`". Version 1 used a resolver (`resolver.define('event-listener', ...)`) and the consumer's `resolver: { function, method }` property; version 2 replaced it with `function:`. Last updated Jun 6, 2025. [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api-version-2-upgrade/] The package on the registry is now `@forge/events@3.0.5`; no page titled for a version 3 upgrade was found, and the API reference describes itself as the latest version. [https://registry.npmjs.org/@forge%2Fevents/latest; https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/]

**Own container? Not established.** No page fetched says whether a consumer invocation shares a container, module scope or `/tmp` with the resolver function that pushed to it. The native runtime page only says "Your app must not persist customer data or sensitive content in global state, in memory or on disk, between subsequent invocations" (last updated Aug 21, 2026). [https://developer.atlassian.com/platform/forge/function-reference/nodejs-runtime/] The two functions are separate `function` modules with separately settable `memoryMB` and `timeoutSeconds`, which is the extent of what is documented.

## 2. Is adding a consumer a major version?

**Documented.** The app versions page (last updated Aug 3, 2026) enumerates the changes that make a major version: "Modifying scope permissions. This includes: Adding a scope. Swapping a scope for one not already listed. Removing a scope."; "Modifying content permissions CSP options. This includes: Adding a CSP option. Swapping a CSP option for one not already listed."; "Modifying external permissions CSP options and URLs. This includes: Adding a CSP option or URL. Swapping a CSP option or URL for one not already listed."; "Adding or modifying web trigger module functions. This includes: Adding a new `dynamic` web trigger. Modifying a `static` web trigger to `dynamic`."; "Adding or modifying the category of an existing egress permission."; "Modifying `inScopeEUD` from `false` to `true` for an egress permission element for the first time."; "Enabling licensing"; "Adding or removing providers"; "Changing a provider client ID"; "In most cases, updating your app's remote backends"; "Adding `permissions.external.configurable.enabled` to enable Customer-managed Egress". Then: "Forge creates a new minor version whenever you deploy app changes that don't result in a new major version." [https://developer.atlassian.com/platform/forge/versions/]

**Consequence, documented by absence.** A `consumer` module, a second `function` module and the `@forge/events` dependency are not on that list, and a consumer needs no scope. On the page's own rule that would make the deploy minor. The page does not say the list is complete, and this repository has recorded a deploy going major for a module type not on it either (`jira:customField`, `docs/adr/0025-the-app-declares-a-business-value-field.md`, `CLAUDE.md`), so the page cannot be read as a guarantee. The CLI is the arbiter: "The CLI linter detects such major changes and warns you before triggering the deployment", and the deploy reference shows the stop, "The deployment failed due to 1 approval requested. Run `forge deploy --approve [ruleName]`", with the rule named `MAJOR_VERSION_RULE` (deploy reference last updated Aug 31, 2026). [https://developer.atlassian.com/platform/forge/versions/; https://developer.atlassian.com/platform/forge/cli-reference/deploy/]

**Does the classification apply while only `development` is installed? Documented that versions are per environment; not established that development is exempt.** "Forge creates and maintains versions on a per-environment basis." The environment-specific consequences the page states are for production only: "when you deploy app changes to `production` resulting in a new major version, this version becomes available for all customer sites in `production`", and "if you deploy a new minor version to a major version in `production`, it will automatically be applied to all customer sites running that major version in `production`". Major upgrades are "not applied to an app installation immediately"; "Site admins can select **upgrade** from the manage apps screen to complete the app upgrade" or "You can use the Forge CLI to complete a major upgrade with `forge install --upgrade`." [https://developer.atlassian.com/platform/forge/versions/] The deploy reference's example message reads "This deployment triggers a major version upgrade in the production environment because: Change due to scope modification", which is the environment that example deployed to, not a statement that other environments differ. [https://developer.atlassian.com/platform/forge/cli-reference/deploy/] The Forge Quest tutorial (last updated Sep 16, 2024) shows the same mechanism on a development environment after a scope change: "We've detected new scopes or egress URLs in your app. Run forge install --upgrade and restart your tunnel to put them into effect", followed by "Your app in the development environment is now the latest". [https://developer.atlassian.com/platform/tool/forge-quest/forge-novice/tutorial-pt3/] So the classification and the `install --upgrade` step apply in development; what is free there, as `CLAUDE.md` records, is the absence of any customer site that has to approve it. The `install` reference (last updated Aug 31, 2026) describes `--upgrade` as "upgrade an existing installation (allowed values: all (default), code)" and `--major-version` as "specify the major version to install", with no environment restriction. [https://developer.atlassian.com/platform/forge/cli-reference/install/]

## 3. The consumer's time and memory, and whether changing them is major

**Timeout. Documented, 900 s confirmed.** The invocation limits page (last updated Sep 1, 2026) prints four rows: "Runtime seconds (also includes UI modules invoked by Forge Remote)" 25; "Runtime seconds (events invoked by Forge Remote)" 5; "Runtime seconds (async events and scheduled trigger module)" 900; "Runtime seconds (web trigger, action and rovo:agentConnector modules)" 55. [https://developer.atlassian.com/platform/forge/limits-invocation/] The function module's `timeoutSeconds` is "The maximum timeout, specified in seconds", range 1 to 900, applies to scheduled triggers and async event consumers only, and where a function is shared by several modules "the lowest value applies". [https://developer.atlassian.com/platform/forge/manifest-reference/modules/function/] The default without the property: "By default, async event consumers time out after 55 seconds. You can now configure a timeout of up to 900 seconds (15 minutes)" (long-running function guide, last updated Oct 16, 2025) [https://developer.atlassian.com/platform/forge/use-a-long-running-function/], and "The optional `timeoutSeconds` parameter of the function module specifies the maximum runtime for an async event consumer function, enabling it to run longer than the default of 55 seconds. You can specify up to 900 seconds (15 minutes)." [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/]

**Memory. Documented.** "Default memory limit is 512MB. To change it, use the `memoryMB` setting of the `runtime` property"; "Available memory per invocation" 1,024 MB; ephemeral disk 512 MB in `/tmp`. [https://developer.atlassian.com/platform/forge/limits-invocation/] The manifest reference (last updated Jul 28, 2026) puts `app.runtime.memoryMB` "between 128 MB and 1,024 MB", default 512, overridable "by setting at the function module definition". [https://developer.atlassian.com/platform/forge/manifest-reference/] So the consumer's function can carry `runtime: { memoryMB: 1024 }` while the resolver's keeps the default.

**Is changing `memoryMB` or `timeoutSeconds` major? Not established, and not on the list.** Neither the versions page, the function module page nor the manifest reference classifies either property. Neither appears in the major-version enumeration in section 2, whose closing rule makes everything else minor. [https://developer.atlassian.com/platform/forge/versions/; https://developer.atlassian.com/platform/forge/manifest-reference/modules/function/; https://developer.atlassian.com/platform/forge/manifest-reference/]

**Cost of a long timeout. Documented.** "To keep your compute costs predictable, set `timeoutSeconds` to the smallest value your function needs"; on a crash or out-of-memory "you are charged for the **lower of**: the function's configured timeout (set via `timeoutSeconds`), or the measured execution time". Function duration is priced at $0.000025 per GB-second beyond 200,000 free GB-seconds (pricing page, last updated Jul 23, 2026). [https://developer.atlassian.com/platform/forge/forge-platform-pricing/] For 50 asks at 3.4 s that is about 170 s; a `timeoutSeconds` of 300 rather than 900 bounds what a hung run can bill.

## 4. Payload, queue, rate, retries, and pushing from a resolver

**Limits. Documented (async events limits, last updated Feb 26, 2026).** "Event per request" 50; "Event per minute" 500; "Payload size" 200 KB; "Retry data size" 4 KB; "Payload size for long running functions" 100 KB; "Retry data size for long running functions" 4 KB; "Cyclic invocation limit" 1000. The 200 KB is "the maximum combined payload across events in a single request"; the 100 KB is per event for functions whose timeout exceeds 55 seconds; the cyclic limit counts push requests originating from one initial invocation across the whole chain. [https://developer.atlassian.com/platform/forge/limits-async-events/] The API reference repeats: "A maximum of 50 events can be pushed per request, up to a maximum combined payload of 200 KB." [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/]

**Queue depth. Not established.** No page states a maximum number of enqueued or pending events; the documented ceilings are per request, per minute and per chain.

**Sizing for this app.** Fifty asks as one event would have to fit in 100 KB, since the consumer's timeout will exceed 55 s; the alternative is one event per ask, up to 50 per push, each under 100 KB, with `concurrency: { key, limit }` if they must not run in parallel ("If the `concurrency` field is not provided then there is no concurrency control"). [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/] The board data the calculation needs is better fetched by the consumer than carried in the event.

**Retries. Documented, automatic, no fixed count.** "Async Events that are successfully enqueued are guaranteed to be delivered **at least once** within a defined **retention window**." "The Retention window is a duration of the Async Event's lifetime. It begins when the Async Event is successfully enqueued and lasts for **24 hours**." "Retention window can be extended by another **72 hours**, to a total of 96 hours", the extension being for "processing overhead caused by performance degradation of the Forge platform, retries triggered by platform level errors". "Async Events are automatically retried within the retention window until they are successfully delivered." "Retries use exponential backoff, with intervals reaching up to approximately 15 minutes between attempts." "An event is considered successfully delivered if the invocation does **not** result in a retry request, app level errors, or platform level errors." "If the retention window is exceeded due to app level errors, the Async Event is dropped." [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/]

**A timeout is retried. Documented.** "App-level errors occur when event processing fails due to issues in the Forge app's code or setup, such as: runtime error, function time out, function out of memory, remote endpoint network error, insufficient permissions, reaching invocation limits." "Platform-level errors are failures caused by internal issues within the Forge platform, such as internal server errors, internal platform rate limiting." Both classes are retried within the window. A consumer that overran 900 s would therefore be re-invoked, so a job that can never finish must record that fact in storage or cancel itself, or it will be retried for a day. [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/]

**The consumer sees the retry. Documented.** The `AsyncEvent` passed to the handler has `body`, `jobId` and `retryContext: RetryContext | undefined`; "The `retryContext` property is only populated when the event is being retried, so check that it exists before reading it." `RetryContext` is `{ retryCount: number; retryReason: string; retryData: any; retentionWindow?: { startTime: string; remainingTimeMs: number } }`, with `retryCount` "The number of retry attempts for this event" and `retryReason` "The reason for the retry, which may include app-level error or platform-level error". An app-requested retry returns `new InvocationError({ retryAfter, retryReason, retryData })`; "The maximum `retryAfter` value is `900` seconds (15 minutes)"; the codes are `FUNCTION_RETRY_REQUEST` and `FUNCTION_UPSTREAM_RATE_LIMITED`. [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/] The separate error-handling page (last updated Jun 16, 2026) covers only the push-side errors `PartialSuccessError`, `RateLimitError`, `TooManyEventsError`, `PayloadTooBigError`, `InvalidQueueNameError` and `InvocationLimitReachedError`. [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api-error-handling/]

**Pushing from a Custom UI resolver during an invoke. Documented by example.** The Realtime tutorial (last updated Jul 23, 2026) declares a `macro` with `resolver: { function: resolver }`, a `consumer` with `queue: llm-prompt-consumer-queue` and `function: consumer`, and a `function` for the consumer with `timeoutSeconds: 900`; its resolver is

```javascript
import { Queue } from '@forge/events';
const queue = new Queue({ key: "llm-prompt-consumer-queue" });
resolver.define("sendLLMPrompt", async ({ payload }) => {
  await queue.push([{ body: payload }]);
});
```

and the reason given is that some prompts "may exceed the default function timeout (55s)". [https://developer.atlassian.com/platform/forge/llm-long-running-process-with-forge-realtime/] The API reference describes the use case in the same terms, functions "requiring more than 25 seconds to run" sending events to a consumer with a longer runtime, and places no restriction on which function type may call `push()`. [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/]

## 5. Delay, cancel, and job status

**Delay. Documented.** "The events processing can be delayed up to 15 minutes using the `delayInSeconds` setting", e.g. `queue.push({ body, delayInSeconds: 5 })`. [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/]

**Cancel. Documented.** `push` returns `{ jobId }`; `queue.getJob(jobId)` returns a `JobProgress`; `await jobProgress.cancel()`. "When a job is canceled, any events from that job that have not yet started processing, including retries, will not be processed. This does not affect function invocations that are already being executed." [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/]

**Status. Documented, counts only.** `const { success, inProgress, failed } = await jobProgress.getStats();` Those three numbers are the whole of the documented job status: no per-event state, no result payload, no timestamps. [https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/] A resolver can therefore poll `getStats()` to learn that a job's events have all succeeded or failed, but the sequencing result itself must be written somewhere the poller can read, which is storage (section 6). The `jobId` is available to the consumer on `event.jobId`, so a storage key derived from it works from both ends.

**Job record lifetime. Not established.** No page says how long after completion `getJob(jobId).getStats()` keeps answering, or whether a job id expires.

**Realtime as the alternative to polling. Documented.** Forge Realtime is generally available (last updated Jun 25, 2026); its limit is "50 (3000 events per minute)" operations per second per installation. [https://developer.atlassian.com/platform/forge/realtime/; https://developer.atlassian.com/platform/forge/limits-realtime/] From a consumer "you must use subscribeGlobal() and publishGlobal() because the context-based methods (subscribe() and publish()) are not supported in async execution contexts", and a published event's `eventId` "will be null if the event failed to publish or if there are no existing subscriptions", so a page that has navigated away misses the answer unless it is also in storage. [https://developer.atlassian.com/platform/forge/runtime-reference/realtime-events-api/] The tutorial's own comparison: "no need to coordinate storage reads/writes or handle polling intervals". [https://developer.atlassian.com/platform/forge/llm-long-running-process-with-forge-realtime/] The Forge scopes page (last updated Oct 20, 2025) lists no Realtime scope. [https://developer.atlassian.com/platform/forge/manifest-reference/scopes-forge/] No page fetched says whether Realtime affects Runs on Atlassian eligibility; it is Atlassian-hosted, and the eligibility page's disqualifier list (see the badge note of the same date) does not name it.

**A REST route exists but is not for this. Documented.** `POST /atlassian/forge/events/v1/async-events` submits events, under the "Forge Containers REST API (EAP)" with a `forge-proxy-authorization` header; it is the Container Services path, not a job-status endpoint. [https://developer.atlassian.com/platform/forge/rest/v2/api-group-forge-events/]

## 6. Holding the result in storage for a poller

**Scope. Documented.** "Using the `@forge/kvs` package requires the `storage:app` scope in your manifest file" (KVS API reference, last updated Aug 21, 2026), which this app already declares and justifies in `forge/manifest.yml`. [https://developer.atlassian.com/platform/forge/storage-reference/kvs-api/] The scopes page describes `storage:app` as "Enables the App storage API." [https://developer.atlassian.com/platform/forge/manifest-reference/scopes-forge/]

**Size and rate. Documented (KVS and Custom Entity Store limits, last updated Mar 25, 2026).** Per installation: request rate 1000 RPS; "Read (10KB request per min)" 4000; "Write (10KB request per min)" 4000. Per key: "Maximum length of a key" 500 characters, format `/^(?!\s+$)[a-zA-Z0-9:._\s-#]+$/`; "Maximum size of a single persisted value (in RAW)" 240 KiB; "Maximum object depth permitted" 31; reads 12 MB/s and writes 1 MB/s per key. Transactions: 25 operations, each key once, 4 MB payload, counted as one write. Custom entities add: 20 entities per app, 7 custom indexes and 50 attributes per entity, range attributes 900 bytes and partition attributes 1,700 bytes combined, 100 conditions per complex query. [https://developer.atlassian.com/platform/forge/limits-kvs-ce/]

**TTL. Documented, exists.** `kvs.set(key, value, options?)` takes a `ttl` of `{ unit: "SECONDS" | "MINUTES" | "HOURS" | "DAYS", value }`; "The maximum supported TTL is _1 year_ from the time the expiry is set." "Expired data is not removed immediately upon expiry. Deletion may take up to 48 hours." "During this window, read operations may still return expired results." The expiry is returned "as metadata _only_ when explicitly requested" via the `EXPIRE_TIME` field, in ISO-8601. [https://developer.atlassian.com/platform/forge/storage-reference/kvs-api/] A poller that must not act on a stale row should therefore check the row's own timestamp rather than rely on expiry having deleted it.

**Consistency. Documented.** "The `kvs.get` method, on the other hand, is strictly consistent. It will always return current data", whereas "The `kvs.query` method used by the Key-Value Store is eventually consistent" (KVS overview, last updated Aug 21, 2026). Write conflicts are "last-write-wins" by default; writes to a key are atomic. [https://developer.atlassian.com/platform/forge/storage-reference/kvs/; https://developer.atlassian.com/platform/forge/storage-reference/kvs-api/] So a poll by exact key sees the consumer's write as soon as it lands.

**Retention after uninstall. Documented.** "Forge hosted storage retains data for 28 days after uninstallation" (storage overview, last updated Aug 21, 2026). [https://developer.atlassian.com/platform/forge/runtime-reference/storage-api/]

**KVS or custom entities?** Nothing in the design needs an index or a query: the page knows the `jobId` it was handed, and `kvs.get` on a key built from it is strictly consistent. Custom entities buy indexed queries at the cost of a schema declared in the manifest, and no page fetched says whether adding an entity declaration is a major version. A sequencing result for 50 asks has to fit in 240 KiB per value, or be split across keys under a transaction of up to 25 operations. The rate budget, 4,000 reads per minute per installation, bounds how many pages can poll how often; a poll every 2 s from one page is 30 reads a minute.

## 7. The resolver's 25 seconds, the bridge, and returning early

**Documented.** The 25 s row in section 3 is the default runtime timeout and is the one a Custom UI resolver runs under; the async events reference frames its use case as functions "requiring more than 25 seconds to run". [https://developer.atlassian.com/platform/forge/limits-invocation/; https://developer.atlassian.com/platform/forge/runtime-reference/async-events-api/] The Custom UI resolver reference (last updated Nov 8, 2024) states no timeout of its own; the callback may return a value or a promise. [https://developer.atlassian.com/platform/forge/runtime-reference/custom-ui-resolver/]

**Bridge `invoke` timeout. Not established.** The `invoke` reference (last updated Jun 19, 2026) gives the signature, `invoke(functionKey, payload?)` returning a promise, the optional metadata form that returns `rateLimitProperties`, and "Invocations from users, webtriggers, or scheduled triggers are subject to Forge's invocation limits"; it states no client-side timeout. [https://developer.atlassian.com/platform/forge/apis-reference/ui-api-bridge/invoke/; https://developer.atlassian.com/platform/forge/custom-ui-bridge/invoke/]

**Payloads across the bridge. Documented.** "Front-end invocation request payload size" 500 KB; "Front-end invocation response payload size" 5 MB; "The maximum request payload size for an invocation" 5 MB. Rate: "1,200 per minute" per user; "5,000 per minute and 300 per second (whichever is hit first)" per install, and the changelog of Sep 1, 2026 raised the per-installation figure to "300 requests per second (RPS) or 7,000 RPM" and removed the per-environment cap. [https://developer.atlassian.com/platform/forge/limits-invocation/; https://developer.atlassian.com/platform/forge/changelog/]

**Returning before the work completes. Documented by example.** The tutorial resolver in section 4 awaits only the push and returns; the consumer runs afterwards under its own 900 s. Nothing fetched says a resolver's invocation is held open for work it enqueued. [https://developer.atlassian.com/platform/forge/llm-long-running-process-with-forge-realtime/]

## 8. Function bundle size

**Not established.** The resource limits page (last updated Jul 7, 2026) documents static resources only: "Maximum bundle size in megabytes (MB) for a resource" 100 MB, 5,000 files per resource, 50 resources, 25,000 files and 1 GB cumulative, introduced by "There are limits on the number and size of static resources that can be bundled with your app if you use Custom UI or UI Kit." [https://developer.atlassian.com/platform/forge/limits-resource/] The manifest reference caps `manifest.yml` at 200 KB. [https://developer.atlassian.com/platform/forge/manifest-reference/] The `build` reference (last updated Aug 31, 2026) adds only `--inspect` ("save application bundle for inspection") and the `deploy` reference nothing on size. [https://developer.atlassian.com/platform/forge/cli-reference/build/; https://developer.atlassian.com/platform/forge/cli-reference/deploy/] The probe's 17.7 MB zip therefore sits under an undocumented ceiling, which is the same position the badge note of this date recorded.

## 9. Runtime and Pyodide versions

**Documented.** `app.runtime.name` accepts `nodejs24.x` "(recommended)", `nodejs22.x` and `nodejs20.x`; `architecture` is `arm64` or `x86_64`, default `x86_64` (manifest reference, last updated Jul 28, 2026).
