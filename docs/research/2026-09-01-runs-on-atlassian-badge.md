# Can the app recover the Runs on Atlassian badge while running `agent/tools/` unchanged?

Research note, 2026-09-01. Sources are Atlassian's developer documentation, Atlassian community threads, Pyodide's own repository and CPython's own material, fetched today. Each claim is labelled **documented** (Atlassian or the project's own docs), **forum** (a community post, with the poster's status where it could be read) or **not established**. One set of figures is a local measurement made for this note and is labelled as such.

## Summary

1. **Keeping the Cloud Run calculator and having the badge: blocked.** Eligible apps list no `remotes` at all; a declared remote costs eligibility before a byte travels over it, and `forge eligibility` at 5.0.0 already reports both findings from the remote alone.
2. **Pyodide inside a Forge function: works, measured today on a throwaway app (section 6).** WebAssembly instantiates in the native runtime, an 18 MB bundle deploys, a warm container keeps the loaded runtime, and every figure is byte-identical to native Python. Cold load is 6.8 s on Forge's CPU.
3. **The cost is speed, and one route is on the edge.** Facts and forecast calls are 1.3 to 1.5 s warm on Forge, about ten times native. Sequencing is 13.6 s warm and about 21 s after a cold start, against a documented 25 s resolver timeout: technically inside, practically without margin. Nothing about the runtime or the bundle registered as egress.
4. **CPython WASI in a function: undetermined and weaker than Pyodide.** Builds are 14 to 15 MB zipped, Node's `node:wasi` is Stability 1 (experimental) and python.org publishes no binaries; Brett Cannon's builds are unofficial.
5. **Pyodide in the Custom UI iframe: viable on the badge axis, with two costs.** A `.wasm` served from the app's own static resource makes no network call and is not egress, but WebAssembly compilation needs `unsafe-eval` in `permissions.content.scripts` (a major version), and the scheduled weekly brief has no browser to run in.
6. `wasm-unsafe-eval` is not an allowed value in `permissions.content.scripts`; the community reports `unsafe-eval` working for WebAssembly in a Custom UI (2023).
7. **Data residency after removing the remote: documented.** An app whose in-scope data lives only in Forge hosted storage qualifies for `PINNED` "without additional configuration". Removing a `remotes` entry is a minor version.
8. Browser-side fetches from the iframe to a non-default host do count: `fetch.client` is an egress type, and a domain outside the default allow-list must be declared under `permissions.external`, which makes the app ineligible.
9. External images from non-default hosts, and external fonts, scripts or styles from any host, are external resource domains and disqualify.
10. No Forge changelog entry between 2026-08-13 and 2026-09-01 touches eligibility, egress, remotes, the runtime or limits.

## 1. Runs on Atlassian eligibility, as of today

**Documented.** The three criteria: "Apps exclusively use Atlassian-hosted compute and storage", "Apps support data residency that matches data residency provided by the host Atlassian app", and "Customers can control external data egress (for example, analytics and logs) via admin controls". The egress rule: "Your app must not egress data, with the exception of egress for analytics purposes. If your app sends data for analytics and does not send in-scope End-User Data, then it is eligible for Runs on Atlassian." Detection: "Eligibility for the Runs on Atlassian badge is automatically detected and applied on apps that meet the qualifications." Page last updated Jul 14, 2026. [https://developer.atlassian.com/platform/forge/runs-on-atlassian/]

**Documented.** The Marketplace page carries the same criteria and lists the changes that trigger a major version and can invalidate eligibility: "Adding remotes", "Adding or modifying web trigger module functions", "Adding or modifying the category of an existing egress permission", "Modifying inScopeEUD from false to true for an egress permission". Last updated Jan 14, 2026. [https://developer.atlassian.com/platform/marketplace/runs-on-atlassian/]

**Documented.** The disqualifying manifest contents: "Eligible apps do _not_ list any of the following in the manifest: External resource domains, Remotes, Connect modules, Providers, Dynamic web triggers", where "External resource domains" links to `permissions.external`. Eligible apps must also "use data residency-enabled Forge storage, or store data in Atlassian apps using Atlassian app entity properties". Last updated Jul 14, 2026. [https://developer.atlassian.com/platform/forge/runs-on-atlassian-apps/]

**Does merely declaring a remote disqualify? Documented, yes.** The list above is a list of manifest declarations, not of traffic. The project's own record agrees: `forge eligibility` at app version 5.0.0 still reports exactly two findings, "app is using remote services" and "app is egressing data", and the deploy record says both are the calculator, and ADR 0008 states that "declaring the remote costs eligibility even before anything travels over it" [`docs/forge-deployment.md` line 348; `docs/adr/0008-forge-calls-a-hosted-calculator.md`]. **Forum.** Another developer quoted the same output verbatim in August 2025 for a remote that fetched public documentation only: "not eligible for the Runs on Atlassian program. - App is using remote services - App is egressing data"; the replies were not from Atlassian staff and the thread was unresolved. [https://community.atlassian.com/forums/Jira-questions/Issue-with-Forge-remotes-and-quot-Runs-on-Atlassian-quot-program/qaq-p/3090551]

**Does a Custom UI browser-side fetch disqualify? Documented by inference.** The page's table of egress "allowed by default" has rows `images`, `media`, `frames`, `fetch.client` and `fetch.backend`, each with a short list of Atlassian-controlled domains (for `fetch.client`: `api.media.atlassian.com` and the emoji endpoint), and states "If your apps need to access domains not specified above, you must explicitly allow-list them in your app manifest." An allow-listed domain is an external resource domain, which eligible apps do not list. The page does not contain a sentence in the form "a browser-side fetch is egress"; the conclusion follows from `fetch.client` being an egress type. [https://developer.atlassian.com/platform/forge/runs-on-atlassian-apps/] The permissions reference describes `fetch.client` as defining permitted sources for the `connect-src` policy. [https://developer.atlassian.com/platform/forge/manifest-reference/permissions/]

**Do external images or fonts disqualify? Documented by the same inference.** `images` has a default allow-list (the host, `*.wp.com`, `secure.gravatar.com`, `images.unsplash.com`, `api.media.atlassian.com`, `api.atlassian.com`, the emoji and avatar services). There are no `fonts`, `scripts` or `styles` rows, so any external font, script or stylesheet domain must be declared and counts as an external resource domain. [https://developer.atlassian.com/platform/forge/runs-on-atlassian-apps/]

**Documented.** The analytics exception is narrow: "Only `analytics` is supported, but only for pre-approved domains" and "If `inScopeEUD` is set to `true`, then the app is ineligible for Runs on Atlassian" (permissions reference, last updated Jul 20, 2026) [https://developer.atlassian.com/platform/forge/manifest-reference/permissions/]. The pre-approved list is published, and "Using the `analytics` category on a domain that isn't on this list will prevent your app from deploying" (last updated Apr 27, 2026) [https://developer.atlassian.com/platform/forge/analytics-tool-policy/]. Customer-managed egress or remotes also disqualify: "Any app that uses customer-managed egress or customer-managed remotes is not eligible for Runs on Atlassian" (last updated Jun 4, 2026) [https://developer.atlassian.com/platform/forge/customer-managed-egress-and-remotes/].

**Forum (Atlassian staff).** In June 2025 James Dumay, Group Product Manager, described the programme's scope as "compute and storage happen on our platform, with the data lifecycle and egress controls they require", said Connect and Forge Remote apps that "must use partner infrastructure" are "fundamentally misaligned with customers needs", and said that "some forms of egress may be considered in the future if customer needs demand it". Nothing more specific about individual disqualifiers. [https://community.developer.atlassian.com/t/we-need-to-talk-about-runs-on-atlassian/92897] **Forum (status not shown as Atlassian Team).** August 2026: "If you use `static` web triggers to ingress the CI data then your app can still qualify for Runs on Atlassian. If you use `dynamic` web triggers it won't", and eligibility is assessed per app version with the badge reflecting the latest version. [https://community.developer.atlassian.com/t/runs-on-atlassian-eligibility-do-inbound-ci-pushes-and-customer-initiated-import-export-count-as-egress/102219]

**Documented.** The CLI: `forge eligibility` checks "if your app is eligible or not for the Runs on Atlassian program" and "If not eligible, the output of the command displays a list of reasons as well." The reference page does not enumerate the reason strings. [https://developer.atlassian.com/platform/forge/cli-reference/eligibility/]

Documented.** Entries fetched today, newest first: 2026-09-01 updated invocation rate limits (300 RPS or 7,000 RPM per installation, global per-environment cap removed); 2026-08-26 web trigger lifecycle APIs for Container Services; 2026-08-26 site limit removed from the Export app logs API; 2026-08-25 app macros category deprecation; 2026-08-25 Rovo Agent Connector to Preview. ## 2. WebAssembly inside a Forge function

**Runtime. Documented.** The manifest `app.runtime.name` accepts `nodejs24.x` "(recommended)", `nodejs22.x` and `nodejs20.x` (manifest reference, last updated Jul 28, 2026) [https://developer.atlassian.com/platform/forge/manifest-reference/]. The native runtime page says "This runtime supports `Node.js 22` and `Node.js 24`", notes Node.js 20 reached end of life on April 30, 2026, and states "You can import any built-in, local, or third-party Node modules into your app"; outbound connections are "HTTPS only; plain HTTP or TCP connections are not allowed" (last updated Aug 21, 2026) [https://developer.atlassian.com/platform/forge/function-reference/nodejs-runtime/]. This app declares `nodejs22.x` [`forge/manifest.yml`].

**Legacy runtime. Documented, retired.** The legacy runtime was a "Javascript sandbox runtime" simulating Node 14, with "128MB available memory per invocation", deprecated October 29, 2024, and "From February 28, 2025: All Forge apps still running on the legacy runtime version will no longer function." Snapshotting was a legacy feature: "The snapshotting feature is no longer supported in the new native Node.js runtime, as it is no longer required." The native runtime also drops the guarantee that local state is cleared between invocations, so the developer is responsible for not letting customer data persist in module scope. [https://developer.atlassian.com/platform/forge/runtime-reference/legacy-runtime-reference/; https://developer.atlassian.com/platform/forge/runtime-reference/legacy-runtime-migrating/]

**`WebAssembly.instantiate` in the runtime. Not established for Forge; documented for Node.** No Atlassian page fetched mentions WebAssembly, `.wasm` files, native `.node` addons, `child_process`, `worker_threads` or the bundler's handling of binary assets; the native runtime page is silent on all of them. Node itself "provides the necessary APIs via the global `WebAssembly` object" with `compile`, `validate` and `instantiate` [https://nodejs.org/en/learn/getting-started/nodejs-with-webassembly]. Whether Forge's runtime restricts that global, or whether `@forge/bundler` copies a `.wasm` file into the deployed artifact, could not be established from any primary source. No community thread was found reporting WebAssembly running in a Forge *function*; the two WebAssembly threads found are both about Custom UI (section 4). One 2023 thread on `ffmpeg.wasm` concluded it would not run on the backend because the library "depends on node-fetch" and "system calls are limited for customer security" (legacy runtime era; poster ibuchanan, status not verified). [https://community.developer.atlassian.com/t/ffmpeg-edit-video-file/70055]

**Bundle size. Not established.** The resource limits page (last updated Jul 7, 2026) documents static resources only: "Your app can have up to 50 resources, with each resource bundle containing up to 5,000 files and 100 MB", cumulative 25,000 files and 1 GB [https://developer.atlassian.com/platform/forge/limits-resource/]. In September 2024 a deploy failed with "Each resource can only be up to 50000000 bytes (zipped)" [https://community.developer.atlassian.com/t/forge-deploy-gives-size-related-error/83364]; the figure has since been raised to the 100 MB above. No page fetched states a maximum size for the function code bundle; the only file size limit on the manifest reference is "200 KB for the `manifest.yml` file" [https://developer.atlassian.com/platform/forge/manifest-reference/].

**Memory and time. Documented (invocation limits, last updated Sep 1, 2026).** Timeouts: UI modules and Forge Remote 25 seconds; events from Forge Remote 5 seconds; web triggers, `action` and `rovo:agentConnector` 55 seconds; async events and scheduled triggers 900 seconds. Memory: 512 MB default, "1,024MB" available via `memoryMB`; 512 MB ephemeral disk in `/tmp`; 5 MB request payload; 500 KB frontend invocation request and 5 MB response. [https://developer.atlassian.com/platform/forge/limits-invocation/] The manifest reference puts `memoryMB` "between 128 MB and 1,024 MB", default 512, applying to "all the functions at runtime" with per-function override [https://developer.atlassian.com/platform/forge/manifest-reference/]. The function module's `timeoutSeconds` is 1 to 900 and "applies to scheduled triggers and asynchronous event consumers only" (last updated Jan 13, 2026) [https://developer.atlassian.com/platform/forge/manifest-reference/modules/function/]. Async event payloads are capped at 200 KB per request and 100 KB per event for functions with timeouts over 55 seconds [https://developer.atlassian.com/platform/forge/limits-async-events/].

**Cold start. Not established.** No Atlassian page fetched documents cold-start behaviour for the native runtime. The only snapshotting Atlassian documents is the retired legacy feature above. A partner-authored community article lists cold starts among causes of P99 latency without figures. [https://community.atlassian.com/forums/Jira-articles/Understanding-Forge-Invocations-and-Metrics-How-Vendors-Can/ba-p/3204154]

## 3. Pyodide and CPython-on-WASM against those limits

**Size. Documented (Pyodide repository) and measured (npm registry).** The Pyodide docs say "The minimal set of files needed to start Pyodide is included as `pyodide-core-{{VERSION}}.tar.bz2`", that this core set "was designed primarily for Node.js usage", that `npm install pyodide` installs the same files, and that "The full distribution is quite large (200+ megabytes)". [https://raw.githubusercontent.com/pyodide/pyodide/main/docs/usage/downloading-and-deploying.md] The current npm package is `pyodide@314.0.6`, unpacked size 13,874,244 bytes, of which `pyodide.asm.wasm` is 9.60 MB, `python_stdlib.zip` 2.55 MB and `pyodide.asm.mjs` 1.25 MB; `engines.node` is `>=18.0.0` [https://registry.npmjs.org/pyodide/latest; https://data.jsdelivr.com/v1/packages/npm/pyodide@314.0.6]. The changelog dates 314.0.6 to August 25, 2026 [https://raw.githubusercontent.com/pyodide/pyodide/main/docs/project/changelog.md]. The roadmap's figures, "a first load of Pyodide requires a 6.4 MB download" and "the environment initialization takes 4 to 5 seconds", are older than the current build and should not be quoted as current [https://raw.githubusercontent.com/pyodide/pyodide/main/docs/project/roadmap.md].

**Node support. Documented.** "Starting with Pyodide 0.25.0, Node.js < 18 is no longer officially supported." Loading is `import { loadPyodide } from "pyodide"` then `await loadPyodide()`; in Node, `packageCacheDir` is where downloaded packages are cached, and a package not present locally is downloaded from jsDelivr. [https://raw.githubusercontent.com/pyodide/pyodide/main/docs/usage/index.md; https://raw.githubusercontent.com/pyodide/pyodide/main/src/js/pyodide.ts] For stdlib-only code no download occurs; `python_stdlib.zip` ships in the package. Snapshot options `_makeSnapshot` and `_loadSnapshot` exist in `loadPyodide`'s options but are marked `@ignore` (undocumented) [https://raw.githubusercontent.com/pyodide/pyodide/main/src/js/pyodide.ts]. Pyodide's FAQ has no section on memory or startup time. The roadmap states Pyodide "is currently around 3x to 5x slower than native Python".

**Local measurement, not a documented figure.** Made today for this note, Node v26.7.0 on this Mac, `pyodide@314.0.6` (Python 3.14.2), the repository mounted read-only via `mountNodeFS`, `agent/tools/` unmodified:

| Step | Time | RSS |
|---|---|---|
| `loadPyodide()` | 977 ms | 234 MB |
| `metrics.py data/sample-sprint.json` | 63 ms, then 10 ms | 237 MB |
| `forecast.py data/sample-multi-sprint.json --snapshots agent/snapshots/scope.json` | 306 ms, then 201 ms | 238 MB |
| `intake.py data/sample-bundle.json --ask data/asks/INTAKE-2026-014.json` | 12 ms | 238 MB |

Native `python3` 3.14.7 on the same machine: 0.05 s, 0.15 s, 0.05 s. Every stdout and the written facts JSON were byte-identical between Pyodide and native (`cmp`). The imports the tools use are `json`, `argparse`, `datetime`, `statistics`, `random`, `re`, `pathlib`, `glob`, `collections`, `dataclasses`, `typing`, all present in Pyodide's stdlib. Forge's CPU is not this Mac's and the runtime is Node 22 or 24, not 26, so these are a floor, not a forecast; the point is that load plus one forecast is around 1.3 s against a 25 s budget, and 238 MB against 512 MB.

**Local measurement of the slow call, and of the iframe route, not documented figures.** The table above times a single-ask forecast; the calculator's slowest route is `intake.sequence`, which ADR 0008 measured at 3.07 s on Cloud Run. Made today on an Apple M3 Pro with `pyodide@314.0.6`, calling `MT.facts`, `FC.build` and `IN.sequence` (four asks, `board="42"`, `as_of="2026-08-10"`, as `tests/test_agent.py` does) and comparing `json.dumps(sort_keys=True)` output by SHA-256:

All seven outputs, sequencing included, were byte-identical across all four runtimes. Peak RSS in Node was 236 to 239 MB over three runs. Compressed sizes: `pyodide.asm.wasm` 3.53 MB gzip (2.77 MB brotli), `python_stdlib.zip` 2.50 MB gzip, `pyodide.asm.mjs` 0.26 MB gzip, about 6.3 MB gzip in total against a current Forge static build of 628 KB. The browser figures are from the Claude Code Browser pane loading the files from a local static server; the backgrounded column shows what a hidden tab does to a main-thread computation, and a real Custom UI would need the work in a worker for that reason as much as for responsiveness. Sequencing under WASM is three times native on this machine; on Forge's CPU it is an unknown multiple of a 25 s budget, which is the figure the throwaway-app experiment must produce.

**CPython WASI. Documented and measured.** PEP 11: wasm32-wasip1 is Tier 2 ("WASI was a tier 3 platform for Python 3.11 and 3.12, and became a tier 2 platform starting with Python 3.13"); wasm32-emscripten is Tier 3 [https://peps.python.org/pep-0011/]. python.org publishes no WASI binaries; users are pointed at the build scripts [https://discuss.python.org/t/wasi-build-of-3-13-0/66979]. Brett Cannon (CPython core developer) publishes unofficial builds; the current assets are `python-3.14.7-wasi_sdk-24.zip` 14.29 MB and `python-3.13.15-wasi_sdk-24.zip` 13.84 MB, both dated 2026-08-07 [https://api.github.com/repos/brettcannon/cpython-wasi-build/releases]. The 3.13.0 build required a `lib` directory beside `python.wasm` and is run under `wasmtime --dir . python.wasm` [https://discuss.python.org/t/wasi-build-of-3-13-0/66979]. Running it in Node rather than wasmtime would use `node:wasi`, which in Node 22 is "Stability: 1 - Experimental", supports `preview1` and `unstable`, and "does not currently provide the comprehensive file system security properties provided by some WASI runtimes" [https://nodejs.org/docs/latest-v22.x/api/wasi.html]. So the WASI route is no smaller than Pyodide and rests on an experimental Node module; Pyodide's Emscripten build needs only the `WebAssembly` global.

**Community precedent. Forum.** No thread was found in which anyone ran Pyodide or any WebAssembly in a Forge *function*. Python-in-Forge threads from 2022 say "The native Forge runtime only supports JavaScript and TypeScript today" and suggest hosting Python externally [https://community.developer.atlassian.com/t/is-it-possible-to-use-python-within-forge/62413]. PyScript (which is Pyodide) was shown working in a Custom UI in October 2022 by CameliaGao, whom the thread identifies as Atlassian staff, with `unsafe-eval` and external CDN permissions, and the caveat "We do not officially support PyScript" [https://community.developer.atlassian.com/t/pyscript-with-forge/62746]. That example loaded from a CDN, which is egress; it shows the runtime works in the iframe, not that the badge survives.

## 4. The Custom UI iframe side

**Browser-side calls to a non-Atlassian host. Documented by inference, yes they count.** See section 1: `fetch.client` is an egress type with a default allow-list of Atlassian domains, anything else must be declared under `permissions.external`, and eligible apps declare no external resource domains. [https://developer.atlassian.com/platform/forge/runs-on-atlassian-apps/; https://developer.atlassian.com/platform/forge/manifest-reference/permissions/]

**A `.wasm` served as a static resource. Documented in part.** Custom UI is "served with a content security policy (CSP)"; "All scripts and assets used in your Custom UI app must come from the same resource directory" [https://developer.atlassian.com/platform/forge/custom-ui/]. Resources are capped at 100 MB and 5,000 files each, 50 per app [https://developer.atlassian.com/platform/forge/limits-resource/]. A 14 MB Pyodide core fits. Whether Forge serves a `.wasm` file with a `Content-Type` that `WebAssembly.instantiateStreaming` accepts is not established; a March 2025 thread reported that listing a `.wasm` in the resource "didn't work" and was answered in June 2026 by a non-staff poster recommending a CDN instead [https://community.developer.atlassian.com/t/are-web-assembly-files-allowed-in-forge-custom-ui-apps/90421]. `WebAssembly.instantiate` over a fetched `ArrayBuffer` does not depend on the MIME type, so this is a nuisance rather than a blocker, but it was not tested for this note.

**CSP and `wasm-unsafe-eval`. Documented.** The allowed values for `permissions.content.scripts` are `unsafe-inline`, `unsafe-hashes`, `unsafe-eval`, `blob:` and `<sha-algorithm>-<base64-value>` with `sha256`, `sha384` or `sha512`. `wasm-unsafe-eval` is not among them, and no default CSP is printed on the page. [https://developer.atlassian.com/platform/forge/manifest-reference/permissions/] The iframe page lists the sandbox flags (`allow-downloads`, `allow-forms`, `allow-modals`, `allow-pointer-lock`, `allow-same-origin`, `allow-scripts`) and says nothing about WebAssembly (last updated Nov 11, 2024) [https://developer.atlassian.com/platform/forge/custom-ui/iframe/]. **Forum.** In August 2023 a developer hit "Refused to compile or instantiate WebAssembly module because 'unsafe-eval' is not an allowed source of script", added `unsafe-eval` under `permissions.content.scripts`, and after `forge deploy` and `forge install --upgrade` WebAssembly compiled; a web worker needed to be created from a `blob:` URL to inherit the parent CSP. CameliaGao replied with a working example; her badge could not be verified from the fetched page. [https://community.developer.atlassian.com/t/is-there-anything-special-need-to-get-unsafe-eval-working/72127] **Documented.** "Modifying content permissions CSP options. This includes: Adding a CSP option" is a major version change (app versions, last updated Aug 3, 2026) [https://developer.atlassian.com/platform/forge/versions/]. `unsafe-eval` is a content permission, not an external one; nothing fetched says a content CSP option affects badge eligibility, and the ineligibility list names external domains only.

**What the iframe cannot do for this app.** The weekly brief runs from `scheduledTrigger` in a function with no browser [`forge/manifest.yml`]. A browser-hosted calculator leaves that path with no calculator, so the iframe route is at most half an answer unless the function route also works.

## 5. Data residency and versioning after removing the remote

**Documented.** "All in-scope End-User Data is stored exclusively in persistent Forge hosted storage: If your app uses only persistent Forge hosted storage for all in-scope End-User Data, it qualifies for `PINNED` status without additional configuration." Forge presumes remote storage of in-scope data if the manifest includes "An external domain defined in fetch" or "Any remote without operations defined". `PINNED` is the only named status on the page; the phrase "Atlassian-managed" does not appear. "When an admin installs an eligible Forge app on an Atlassian app that is already `PINNED`, the app will automatically be displayed as `PINNED` as well." Last updated Jul 14, 2026. [https://developer.atlassian.com/platform/forge/data-residency/] What counts as in-scope End-User Data is left to the developer: "You are responsible for defining, documenting, and communicating with your customers what data is in-scope and out-of-scope" [https://developer.atlassian.com/platform/forge/in-scope-end-user-data/].

**Documented.** "Removing a remotes entry or any update that decrease an existing remote's scope will only result in a minor upgrade." Adding a `remotes` section, changing `baseUrl`, adding or removing region URLs, and flipping `inScopeEUD` to `true` are major (remotes reference, last updated Jun 19, 2026) [https://developer.atlassian.com/platform/forge/manifest-reference/remotes/]. The app versions page's major list is additive throughout ("Adding a scope", "Adding a CSP option or URL", "Adding or modifying the category of an existing egress permission") and does not list removal of remotes or of external permissions [https://developer.atlassian.com/platform/forge/versions/]. Neither `forge lint` nor `forge deploy` documentation fetched says anything about classifying removal of egress beyond this. The `forge eligibility` reference does not say whether a newly eligible version changes the badge before it is promoted to production; the forum post in section 1 says the badge follows the latest version.

**Consequence for this repository.** Deleting the `remotes` block is minor and needs no reinstall. Adding `unsafe-eval` under `permissions.content.scripts` for the iframe route is major, and the window for a free major closes at the September external install [`CLAUDE.md`; memory note]. Running Pyodide in the resolver function needs no manifest change at all beyond dropping the remote, which is why it is the route worth testing first.

## 6. The experiment: Pyodide in a Forge function, run today

A throwaway Forge app (`wasm-probe`, webtrigger template, `nodejs24.x`, `memoryMB: 1024`, `architecture: arm64`, deployed to its own `development` environment and installed on the dev site) carried the five tools, two datasets and four asks as embedded strings, and the five Pyodide 314.0.6 runtime files as base64 inside the function bundle. At invocation it unpacked them to `/tmp/pyodide/`, imported `pyodide.mjs` through a dynamic import the bundler could not rewrite, called `loadPyodide({ indexURL })`, and ran the same probe as section 3. Measured, not documented:

**The three unknowns, settled.**

- **WebAssembly runs in a Forge function.** `typeof WebAssembly` is defined, a 9.6 MB module instantiates, and every figure is byte-identical to native Python, sequencing included. The runtime is Node v24.18.0 on Linux arm64 with two CPUs reported, the code at `/var/task`, an AWS Lambda wrapper at `/mnt/wrapper`.
- **The bundle limit is not the constraint.** An 18.0 MB `src/` (a 17.7 MB zip) deployed and ran. Babel warned that `assets.js` exceeded its 500 KB styling threshold and carried on. The Forge bundler is webpack: it shipped only `.cjs` output, dropped `pyodide.asm.mjs`, the `.wasm` and the stdlib zip from `node_modules`, and rewrote Pyodide's own dynamic import into a lazy namespace that fails, which is why the files travel as base64 and load from `/tmp`.
- **A warm container keeps the loaded runtime.** A module-scope Pyodide instance survived three invocations over 42 seconds, so the 6.8 s load is paid once per container, not per call.

RSS was 189 MB before the load and 282 to 286 MB after, against the 1,024 MB requested. Forge's CPU ran the WASM about 3.3 times slower than the M3 Pro did, and about ten times slower than native CPython on the same laptop; ADR 0008 measured sequencing at 3.07 s natively on Cloud Run.

**What that means against the documented limits.** A facts or forecast call is 1.3 to 1.5 s warm and about 9 s cold, inside the 25 s resolver timeout with room. Sequencing is 13.6 s warm and about 21 s cold once the load is added, which is inside 25 s on paper and not by a margin anyone should ship: a slower container, a larger board or a fifth ask puts the first call after a cold start over the line. The 900 s budget for scheduled triggers and async events is not in question, so the weekly brief is unaffected. This was measured through a web trigger, whose own timeout is 55 s; the 25 s figure for a resolver is documented rather than exercised here.

**Eligibility.** `forge deploy --verbose` printed the rule set by name: `HAS_REMOTES`, `HAS_CONNECT_MODULES`, `HAS_DEFINED_EGRESS`, `HAS_EXPOSED_CREDENTIALS`, `HAS_EGRESS_WEBTRIGGER_MODULE`, `HAS_PERSONAL_API_TOKEN_USAGE`, `HAS_ENABLED_CONFIGURABLE_EGRESS`. The throwaway failed only `HAS_EGRESS_WEBTRIGGER_MODULE`, because the template's web triggers use `response.type: dynamic`; `forge eligibility` phrases it as *"App is using a webtrigger module that can egress data"*, and that is the only finding. Nothing about an 18 MB bundle, WebAssembly or `/tmp` writes registered as egress. The deploy from 2.0.0 to 2.1.0, which added the runtime files, was classified a minor version.

**Not done.** The app is still installed on the dev site and its development environment still holds version 2.1.0; removing it is `forge install --uninstall` (or uninstalling from the site's app management) followed by deleting the app. No production environment was touched. Pyodide's undocumented `_makeSnapshot` and `_loadSnapshot` options, which might cut the 6.8 s cold load, were not tried. Splitting sequencing into an async event with the 900 s budget was not tried either; it would change the resolver's shape from a synchronous answer to a job the page polls.

## What could not be established from primary sources

- Whether Forge's native Node runtime permits `WebAssembly.instantiate` in a function; Atlassian documents nothing either way, and no community report of WebAssembly in a function was found.
- Whether `@forge/bundler` includes `.wasm` and `.zip` files from `node_modules/pyodide` in the deployed function artifact, and whether Pyodide's loader finds them at its computed `indexURL` inside that artifact.
- Any maximum size for the function code bundle. Only static resource limits (100 MB per resource) and the manifest file (200 KB) are documented.
- Cold-start latency for the native runtime, and whether a warm container's module scope survives between invocations reliably enough to keep a loaded Pyodide instance; Atlassian says only that state is no longer guaranteed to be cleared.
- Forge's CPU relative to the machine used for the local measurement, so the 1.3 s figure is a lower bound.
- Whether Forge serves a static `.wasm` with an `application/wasm` content type.
- Whether CameliaGao carries the Atlassian Team badge in the two threads cited; the fetched pages did not render badges.
- The exact reason strings `forge eligibility` can emit; the CLI reference does not list them. The two this app receives are known from its own deploy record and one community post.
- Whether adding `unsafe-eval` under `permissions.content.scripts` has any bearing on eligibility; the documented disqualifiers are external domains, remotes, Connect modules, providers and dynamic web triggers, and content CSP options are not mentioned in either direction.
- The term "Atlassian-managed" for data residency; the documentation uses `PINNED` and "eligible".
- Forge changelog entries older than 2026-08-13; the page is paginated to 85 pages and only the first was read.
- Pyodide's memory footprint and load time in Node from Pyodide's own documentation; neither is documented, so both figures above are local measurements.
