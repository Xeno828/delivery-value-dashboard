# The calculator is reached by `invokeRemote`, region-pinned, and authenticated by the invocation token

[ADR 0008](0008-forge-calls-a-hosted-calculator.md) settled that a Forge build posts to a hosted service rather than growing a second Monte Carlo in JavaScript. It did not settle how the app reaches that service, and the two obvious answers turn out not to be equivalent.

The app calls the calculator with **`invokeRemote()` from `@forge/api`**, against a `remotes` entry whose `baseUrl` is an object of region-specific URLs and whose `operations` are `[compute]`. Atlassian attaches an invocation token; the service verifies it against Atlassian's JWKS and binds the installation identity out of `app.installationId`. The service holds no secret of its own, and holds no opinion about which region a tenant belongs in.

The alternative was a bearer secret over plain `fetch`, and it is the one that was nearly taken — the app already had the `fetch` call written, the service already had a shared-secret mode implemented and tested, and adding an `Authorization` header from an encrypted Forge variable is a smaller diff than any of the above. What ruled it out was not authentication at all. It was that **`fetch(process.env.CALCULATOR_URL + path)` is one URL for every installation on earth.** Region pinning is resolved by Forge from the manifest, per install, using the customer's own Atlassian data residency setting. An app that constructs its own URL cannot take part in that, so it would have to route tenants to regions itself — and to route on a tenant it would need to identify one, which is exactly the capability a single shared string does not have. The cheaper option required inventing, worse, the mechanism the other option gets for nothing.

That is the whole decision. The rest follows from it: because Forge picks the region, the app has no residency logic to get wrong and no table to keep current; because the token identifies an installation, the access log can name who a request was for; because there is no shared secret, there is nothing to rotate and nothing that leaks from a deploy log.

**What it costs.** Three things that would have been free on the `fetch` route. A `baseUrl` that changes format — or gains a region, or changes at all — is a **major version change**, so every region this app will ever offer is cheapest to declare before the first external install and expensive to add afterwards; picking regions becomes a decision with a deadline attached. The verifier's availability now depends on Atlassian's JWKS endpoint, mitigated but not removed by a cached, rate-limited key lookup. And the token has a life measured in seconds, which makes cold-start latency a correctness concern rather than only a performance one — a platform slow enough to start would produce expired-token rejections that look exactly like a misconfigured verifier.

**Also rejected: a hosting platform without a real zero.** The service is idle most of a working day and busy for minutes of it, so the only cost line that behaves like a subscription is the floor. AWS App Runner keeps a provisioned container instance warm by default and bills it whether or not anything calls it — more, doing nothing, than the chosen platform costs at half a million calls a month. Fargate has no scale-to-zero at all and needs a load balancer billing beside it. Both were rejected on the shape of the bill rather than on any number in it, which is why neither needed pricing to a decimal to be ruled out.

**Also rejected: putting an adapter in front of the service to fit a function runtime.** AWS Lambda is the cheapest option costed and stays inside its free tier past a million calls a month. It wants a WSGI adapter, and this product's claim is that every figure traces to one implementation with nothing doing work in between ([0005](0005-tools-compute-the-agent-narrates.md)). An adapter computes nothing; it is still a component that would have to be shown to compute nothing, in the one part of the system whose entire argument is that there is nothing there.

**Also rejected: an IP allow-list as the access control.** Atlassian publishes its egress ranges and recommends against allow-listing them the way one would have to — they shift with latency-based routing, and they carry every Atlassian customer's outbound traffic, so a list built from them admits all of Atlassian rather than this app. A token that proves both *from Atlassian* and *minted for this app* is strictly the stronger claim, and it is the one already implemented.
