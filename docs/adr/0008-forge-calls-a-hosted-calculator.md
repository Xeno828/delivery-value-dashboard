# If we ship on Forge, Forge calls a hosted calculator

Forge runs Node in Atlassian's sandbox and cannot execute `agent/tools/`. The obvious readings of that are both bad: port the Monte Carlo to JavaScript, or drop the forecast from the Forge build. The first is a second implementation of a number we already compute, which is the thing [0005](0005-tools-compute-the-agent-narrates.md) exists to prevent and which we already refused once when the forecast tile chose an offline notice over recomputing itself in the browser. The second sells a delivery product with the delivery forecast removed.

So the Forge app pulls the issues, projects them to the fields a calculation needs, and posts that to a small hosted service that imports the existing Python unchanged. One implementation of every figure, still.

Three measurements made the decision rather than the argument:

**The tools are already pure functions.** Every `open()` and `glob` in `metrics.py`, `forecast.py` and `intake.py` is inside `main()`. The library entry points take a dict and return a dict, and `serve_live.py` has been a thin HTTP wrapper over exactly those calls since live mode shipped. The service is not new code so much as a second caller.

**A call is 16 KB and does not grow with the customer.** A forecast needs one team's history, not the organisation's: 16.2 KB for a 242-issue file and 16.3 KB for a 5,538-issue one, against 158 KB and 3.6 MB for the whole datasets. Compute is 0.25s for the small file and 0.74s for the large; `intake.sequence` is the slow one at 3.07s and the only call within an order of magnitude of a request timeout.

**No issue title has to leave Atlassian.** Running `forecast.build()` against a dataset stripped to `key, created, started, resolved, statusCategory, storyPoints, priority, dueDate, flagged, addedMidSprint` produces byte-identical figures. The only fields that differed were `summary` and `assignee`, echoed back inside `item_risk.items[]` for display, and Forge already holds those — it re-attaches them by key after the call. Titles are the sensitive payload here; it is why `data/dashboard-data.json` is git-ignored and most of what permission mirroring is about.

That last point is what makes the service defensible rather than merely possible. It holds no credential, stores nothing, and cannot reach Jira: Forge owns the grant and does the pulling. It is a calculator that receives dates and status categories. On the credential axis this is *better* than the fetcher we ship today, which holds the token itself.

The costs are real and none of them is a surprise. Egress disqualifies the app from the **Runs on Atlassian** badge, which is a marketing loss with no engineering answer. `forge eligibility` states it as two findings rather than one — *app is using remote services*, *app is egressing data* — so declaring the remote costs eligibility even before anything travels over it. There is no arrangement of this design that keeps the badge, which makes it a cleaner trade than it first looked: the choice is the badge or a second implementation of the forecast, with nothing in between — a sentence corrected in the amendment at the end of this record. The egress declaration is something Marketplace review will read. Data residency stops being Atlassian's problem and becomes ours, pinned per region — that is already roadmap item 6, so it moves earlier rather than appearing from nowhere. And we would be operating a service: uptime, deploys, someone carrying a pager. Stateless and sub-second means scale-to-zero fits, which keeps that bill and that pager quiet.

Rejected: **porting the tools to JavaScript.** It buys the badge and costs the property the whole product rests on. Two implementations of a seeded Monte Carlo will eventually disagree about one sprint, and the day they do, every number in the product becomes something a reader has to check rather than read.

Rejected: **the Forge app storing pulled issues in Forge storage and computing there.** Same second-implementation problem, plus it turns a stateless calculator into a data controller inside Atlassian's platform, which is the harder half of permission mirroring brought forward with none of the benefit.

One thing this record did not anticipate, found on the first real deploy. A Forge Custom UI iframe serves static resources under a CSP that blocks inline `<style>` and inline `<script>`, and blocks them silently — the page renders with the browser's default stylesheet, none of its JavaScript runs, and it reads as a broken build. `dist/` is one file with one inline style block, four inline script blocks and no external references, which is [0001](0001-single-self-contained-html-file.md)'s defining property and precisely what this host will not serve.

That does not change the decision, but it changes what "ship the dashboard on Forge" costs. `build.py --split` emits the same four sources as linked assets, so it is one assembly declining to inline rather than a second implementation, and the suite asserts each emitted asset is byte-identical to `src/`. The single file remains the product; the Forge iframe gets the same sources arranged for a host that forbids inlining. Worth noting the inline JSON seed survives — it is data the page reads rather than script the browser executes.

That fix was half of the finding, and the other half sat in the tenant for the length of every deploy since. `style-src` without `unsafe-inline` also discards the **attribute** form — every `style="..."` the renderers write — and the split build did nothing about it because it only moved the `<style>` and `<script>` *elements*. The failure is much quieter than a page in Times New Roman: the page renders correctly and loses the coloured half of itself. The fill inside every KPI progress bar, the severity disc beside each narrative point, every chart legend swatch, the release progress bars. A bar keeps its track and a disc keeps its glyph, so it reads as a design that always looked like that. 155 elements on the sample sprint, and the only trace was a console line.

`permissions.content.styles: ['unsafe-inline']` in the manifest would have fixed it in one line, and is rejected for the same reason `--split` exists: this repository has twice chosen to change what it emits rather than ask a host to relax a policy, and a style policy is the one still doing useful work next to a renderer that concatenates issue summaries into HTML. Removing seventy-odd `style=` attributes from the render functions is rejected too — it would make the single file's own layout depend on its JavaScript, which is [0001](0001-single-self-contained-html-file.md)'s property spent to fix somebody else's host.

The CSSOM is not policed the same way: `el.style.cssText = …` applies where the identical string in an attribute does not. So `src/app.js` feature-detects whether the host discarded an attribute it just set, and if it did, wraps the `innerHTML` setter once to hand each element the attribute the browser kept back. Where inline style is permitted — every build of `dist/` — the detection is false and none of it runs. The wrap is at the setter rather than at each of the seventy call sites because a missed call site is a tile that silently loses its colour in somebody's tenant, which is the failure this whole entry is about.

Not decided here: whether we ship on Forge at all. OAuth 2.0 (3LO) in `scripts/jira_auth.py` is the working connection and needs none of this. This records what the Forge route costs, so that choosing it stays a decision.

`service/` is the calculator, `forge/` the app that calls it, and `docs/organisation-config.md` explains why the calendar travels in the payload rather than being configured at either end.

## Amended 2026-09-01: there is something in between, and this is its price

This record says the choice is *"the badge or a second implementation of the forecast, with nothing in between."* That was true of the platform as read on 2026-08-25 and it is false in fact. A third shape exists: **the existing Python in `agent/tools/`, unchanged, running under Pyodide — CPython compiled to WebAssembly — inside the Forge function.** One implementation of every figure, no remote, no egress. It was not considered when this record was written, and it was measured rather than argued on 2026-09-01, on a throwaway Forge app that has since been deleted. `docs/research/2026-09-01-runs-on-atlassian-badge.md` §6 has the full account; what follows is what a decision needs.

**What the measurement established.** Forge's native runtime is Node 24 on Linux arm64 and permits `WebAssembly.instantiate`. An 18 MB function bundle deploys without complaint. A warm container keeps a module-scope runtime across invocations, so the load is paid once per container rather than per call. Every figure — facts, both forecasts and a four-ask sequencing — is byte-identical to native CPython under 3.9 and 3.14, SHA-256 compared; the fixed seed carries across the runtime change. And none of it registers as egress: `forge deploy --verbose` prints the eligibility rules by name, and a function carrying a WebAssembly runtime trips none of them.

**What it costs, measured on Forge's CPU rather than a laptop.** About ten times slower than native CPython, and unevenly across the six routes:

| Call on Forge | Warm | After a cold start |
|---|---|---|
| Pyodide load | 0 | 6.8 s |
| `MT.facts`, 480 issues | 0.2 s | about 1 s |
| `FC.build`, 480 issues | 1.3 s | about 9 s |
| `IN.sequence`, 4 asks | 13.6 s | about 21 s |

The documented resolver timeout is 25 seconds. Five of the six routes fit with room. **Sequencing fits on paper and without margin**: a slower container, a larger board or a fifth ask puts the first call after a cold start over the line, and the failure is a tile that times out on a customer's first click. The weekly brief is unaffected, because a scheduled trigger has 900 seconds. Memory was 286 MB of the 1,024 MB a function may request.

**Two facts that change what the trade costs, both from Atlassian's documentation.** Removing a `remotes` entry is a *minor* version, so retiring the calculator carries no reinstall and no deadline — this repository's own rule is to confirm that by deploying rather than reading, and a remote *removal* has not yet been classified by a real deploy of this app. And an app whose in-scope data lives only in Forge storage is `PINNED` for data residency with no configuration at all, which is the half of residency [0012](0012-the-calculator-is-reached-by-invokeremote.md) and [0030](0030-the-manifest-commits-to-its-hostnames-and-realms-once.md) exist to carry.

**What taking the route would mean.** The bundler is the first obstacle and it is solved: Forge's webpack ships only compiled JavaScript and rewrites Pyodide's own dynamic import into something that fails, so the runtime's five files travel as base64 inside the bundle and are unpacked to `/tmp` on first invocation. The validation layer in `service/app.py` — the projection, `MAX_ASKS`, the refusals — is Python and moves in-process rather than away; `tests/test_service.py`'s byte-for-byte parity assertion becomes the test that the in-function answer equals the tool called directly. Sequencing needs a different shape before anything else: an asynchronous event with the 900-second budget that the page polls, or a stated refusal above a board size, or a demonstration that Pyodide's undocumented snapshot options cut the cold load enough — none of which has been weighed. And the calculator is retired last, after the in-function path is validated on a real tenant: three Cloud Run services, three registries, the deploy workflow's region loop and guard, the `remotes` block, and most of [0012](0012-the-calculator-is-reached-by-invokeremote.md) and [0030](0030-the-manifest-commits-to-its-hostnames-and-realms-once.md) go with it, along with the bill and the pager.

**Rejected on the way: Pyodide in the Custom UI iframe.** It avoids the remote too, but WebAssembly compilation in the iframe needs `unsafe-eval` added to `permissions.content.scripts`, which is a major version and so *does* carry the September deadline; a hidden tab ran the same computation at less than half speed; and the weekly brief has no browser to run in, so the iframe is at most half a calculator.

**The decision here is unchanged, and it is now a decision rather than a discovery.** The hosted calculator stands until the user decides otherwise. The trade this record described is real but its terms were wrong: it is not the badge against a second implementation, it is the badge — plus retiring a service somebody carries a pager for — against a forecast ten times slower, a seven-second cold start, and a sequencing route that has to change shape. That is a commercial judgement about what a Marketplace filter is worth against, say, the fortnight a published VPAT would take, and it belongs to the person accountable for it. What this amendment removes is the sentence that said there was nothing to decide.
